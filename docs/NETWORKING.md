# Direct-IP duel networking

The development player now exposes **ONLINE DUEL // DIRECT IP** alongside offline play. Initial host-authoritative gameplay integration has passed a two-process local smoke test. The complete online acceptance criteria are still unproven; this is not a finished release.

## Session integration

The host owns the shared 60 Hz `ArenaSession` authority loop for both human slots, including movement, firing, health, pickups, scoring and respawns. Offline play uses that same loop. Online matches contain no bot participants. An opt-in development validation driver can supply automated input to each process's own human slot.

The client predicts its movement with the shared controller integration and pad logic, retains up to 128 unacknowledged commands, restores the acknowledged host state, then replays remaining commands. Commands are redundantly batched, normalized before encoding and consumed no more than once per host tick. The host sends snapshots every three simulation ticks. The opponent is interpolated six ticks behind the estimated host time. Client-predicted fire produces effects but cannot apply damage; host shot and hit serials replicate combat presentation. Pausing opens local controls while the online authority continues.

Host/join controls accept an IPv4 address and configurable UDP port (default 7777). Both peers must ready up before the countdown. Results use the host winner and offer ready-up for a new round. These paths are implemented; complete timed results/rematch and native-input interaction still need acceptance testing.

## Implemented core

- `DuelSocket`: nonblocking IPv4 UDP with explicit port binding, deterministic disposal and datagrams limited to 1,200 bytes. Receive work is bounded to 64 datagrams per link update; malformed traffic consumes that budget too.
- `DuelProtocol`: versioned binary packets with exact lengths, finite/ranged input validation, two-actor authoritative snapshots and three pickup timers. Inputs contain movement, aim, jump/fire intent, sequence and viewed tick. They cannot carry damage, health or scores.
- `DuelLink`: one remote peer, build-identity comparison, cryptographically random client nonce, address-bound HMAC return-path challenge, session token, retries, ready-state repetition, monotonically newer packet acceptance and eight-second timeout. Advancing the round clears ready state. The application supplies the same nonzero build fingerprint to both peers.
- `DuelInputQueue`: bounded reordering/deduplication of redundant input batches, at most one movement step per authority tick, and short motion continuation on loss. Jitter bursts use the newest movement instead of creating permanent backlog. Brief fire and jump inputs are preserved; a buffered fire retains its original aim and viewed tick. It never repeats fire/jump intent without a new command. Input sequences start at one and a new queue is created each round.
- `BuildIdentityGenerator`: automatically hashes runtime assets/code, package manifests and project settings before a player build. Text line endings are normalized so Git checkout conventions do not produce false incompatibility. Editor and test code, validation captures and the generated identity itself are excluded. The generated SHA-256 resource exposes a 64-bit wire token through `BuildIdentity`. Verification confirmed repeatability, line-ending independence, content-change detection and restoration of the original hash after removing a temporary probe (`Validation/network-build-identity.json`).

The transport follows [.NET's documented nonblocking UDP behavior](https://learn.microsoft.com/en-us/dotnet/api/system.net.sockets.socket.receivefrom). No service accounts, discovery servers or cloud relays are involved. The challenge verifies return-path access; it does not encrypt traffic or provide account identity or protection against an on-path attacker.

## Evidence

`Validation/network-core-editmode.json` records 20 passing cases: the previous 11 simulation/character cases and nine networking cases. Networking checks exercise real loopback UDP sockets: handshake, build mismatch, ready state, command and snapshot delivery, round reset, graceful leave, missing-peer timeout, port rebinding, oversized packets, wrong-session and reordered traffic, forged challenge responses and a full host. Codec tests also reject every prefix of a valid input datagram, trailing bytes, invalid values and 2,000 random datagrams. The input queue verifies deduplication, ordering, bounds and the per-tick consumption limit.

These are transport and protocol tests, not two-client standalone match acceptance, simulated internet impairment, or remote-network verification.

`Validation/online-session-editmode.json` records 22 passing cases after integration, including authoritative replica state and outbound normalization regressions. `Validation/online-session-build.json` records the successful Windows build.

`Validation/Duel-Corrected/host.json` and `client.json` record two separate hidden Windows player processes connected over real loopback UDP with automated inputs. The host recorded 30 shots, 13 deaths and 10 pad launches. The client received 898 snapshots, acknowledged 2,690 inputs and measured a maximum continuous-life prediction correction of 0.0449 m. Both reported zero errors and passed. Reports are sampled separately, so their final ticks and shot counts need not match. This 45-second smoke test does not reach the ten-minute results boundary or prove rematch, impairment tolerance or internet connectivity.

The initial run is retained under `Validation/Duel-Initial`: client serialization failed because rotated unit movement occasionally produced a component of `1.00000012`. Sender normalization fixes this without relaxing the receiver's bounds. The corrected run observed 99 such normalizations and no serialization errors. Reusing the shared authority also passed a fresh seven-bot offline soak (`Validation/online-change-offline-regression.json`): 143 shots, 62 deaths, four pickups, 45 pad launches, zero errors and zero void deaths.

The connection panel was visually inspected in a live, advancing Editor session. Its button action was invoked through Unity APIs; native keyboard entry and mouse interaction are not established by that capture.

## Remaining integration

The host now keeps a bounded pose history and validates viewed ticks up to 12 ticks (200 ms) behind the current authority tick. Local/offline shots use the current pose; remote shots use their displayed opponent tick. The firing origin and direction remain host-owned. Traces use pooled copies of the actual box/capsule hurtboxes, preserve nearest static-world obstruction, and ignore dead targets and poses from an earlier target life. Expired, future and unavailable times cannot produce player hits; they still consume the valid weapon cooldown. Live actors are never repositioned for rewind. All actors move before the current pose is captured and shots are resolved.

`Validation/rewind-editmode.json` records 27 passing cases, including a moved target hit at an earlier pose, the exact twelve-tick limit, expired/future/missing ticks, static walls, respawn isolation, host-owned firing origin and scaled/rotated capsule parity. The implementation uses [Collider.Raycast](https://docs.unity3d.com/6000.6/Documentation/ScriptReference/Collider.Raycast.html) for exact primitive traces and synchronizes temporary transforms before querying, per [Unity's physics API](https://docs.unity3d.com/6000.6/Documentation/ScriptReference/Physics.SyncTransforms.html). Proxies remain in the physics scene during queries and are disabled immediately afterward and destroyed by their owner.

The rebuilt player passed another two-process loopback soak (`Validation/Duel-Rewind/`). At the host sample, each player slot had fired 12 shots; 12 remote shots used validated rewind, with zero rejected timestamps, 12 deaths and 11 pad launches. Both processes logged zero errors. The client received 898 snapshots and measured maximum continuous-life correction of 0.1675 m. The fresh offline soak also passed: 138 shots, 62 deaths, four pickups, 46 pad launches, zero errors and zero void deaths (`Validation/rewind-offline-regression.json`). These are 45-second hidden-window automated runs, not complete timed match, visible performance or native-input acceptance.

Prediction/interpolation, rewind and replicated presentation still need complete impairment and visual acceptance. Full-match/rematch evidence and remaining candidate checks are detailed below; standalone disconnect/error scenarios are not yet complete. Native connection-panel mouse and text-entry checks are recorded below, while keyboard/gameplay feel and human-to-human native acceptance remain open. Actual internet play requires a remote machine and network setup; loopback evidence cannot substitute for that test.

## Extended acceptance tooling and findings

`tools/Test-Duel.ps1 -FullMatch` keeps the normal ten-minute clock, records the first result, readies both peers for a rematch and requires round two to advance at least 900 ticks. The coordinator compares both peers' winner, end tick and final scores. The full-match run for fingerprint `9c50d65e...` passed (`Validation/Duel-FullMatch/`): both reported tick 36,180, winner 0 and final scores 96-69. First-round shot counts were 215 and 208. Both then entered round two and advanced to ticks 900/902. The run took approximately 619 real seconds with zero errors. Its maximum client correction was 1.4100 m. This earlier build predates the subsequent fresh-input queue fix; it is not evidence of a full impaired match on the latest candidate.

`tools/Test-ImpairedDuel.ps1` launches a local-only UDP relay and two players. Defaults are 25 ms one-way delay, +/-10 ms jitter, 5% per-packet loss and seed 7191. The relay records actual applied delays, drops and reordered sends. It uses the standard [Python socket](https://docs.python.org/3.14/library/socket.html) and [select](https://docs.python.org/3.14/library/select.html) APIs; Python 3.14 was used locally. This simulates conditions around a loopback connection and does not test router/NAT behavior or an actual internet path.

The initial relay run stopped on a Windows status-file replacement collision. Status publishing now retries transient sharing errors without stopping packet delivery. The next run stayed connected but failed gameplay acceptance: the oldest-first command queue retained a jitter backlog and all 23 remote shots exceeded the rewind limit. Both failed reports are retained under `Duel-Impaired-50ms` and `Duel-Impaired-50ms-Corrected`.

The fresh-input fix passed 28 tests (`Validation/jitter-editmode.json`) and a separate candidate build (`Validation/jitter-build.json`). Its 60-second impaired smoke test passed (`Validation/Duel-Impaired-FreshInputs/`): 39 host-authoritative shots, 17 validated remote rewinds, one expired timestamp and zero errors. The relay forwarded 5,299 packets, dropped 309 and observed 211 reordered sends; mean applied one-way delay was 29.75 ms. The client acknowledged 3,572 inputs with five pending and measured a maximum continuous-life correction of 0.9911 m. That correction remains a visual-quality concern; passing activity counters is not movement-feel approval.

Native Windows input checks now cover opening the connection panel, editing the UDP port, an unused-host timeout, starting practice and mouse firing. Keyboard movement/jump/pause, settings, and a complete human-to-human native duel remain unverified. See `Validation/native-ui-checks.json` for the precise observations and limits.

Candidate fingerprint `8fff9da2...` also passed its complete real-time impaired match/rematch (`Validation/Duel-FullMatch-Impaired/`). Both peers reported tick 36,180, winner 0 and scores 102-66, with 198 shots from each slot in round one. Both entered round two for at least 900 ticks and logged zero errors. The relay ran approximately 629 seconds, forwarded 51,915 packets, dropped 2,823 and observed 2,020 reordered sends. Mean applied one-way delay was 29.68 ms. Maximum raw client correction was 1.2060 m. This proves the recorded automated local-network conditions, not a real internet path or visual approval.

Correction diagnostics (`Validation/Duel-Correction-Diagnostics/`) identified an unaccepted predicted jump and two-tick airborne time realignment among the larger corrections. The diagnostics preserve raw predicted/authority/replayed positions and grounding/pad state. Physical reconciliation remains immediate and host-authoritative; these measurements are not reduced or hidden by view smoothing.

The presentation-only `ReconciliationView` preserves camera continuity while its offset decays exponentially, checks static-world obstruction and resets on life/round changes or corrections beyond four metres. Host and offline camera paths are unchanged. All 32 tests passed (`Validation/view-reconciliation-editmode.json`), including continuity, frame-partition independence, reset and wall checks. A separate 60-second impaired smoke test passed for fingerprint `9682ead9...` (`Validation/Duel-View-Reconciliation/`): 40 authoritative shots, 19 validated remote rewinds, one expired timestamp and zero errors. Its raw correction maximum was 1.1975 m. Visual feel remains unapproved; this candidate has not repeated the full ten-minute impaired test. Earlier and latest artifacts remain distinguished by their fingerprints.

For a local development smoke test, run `tools/Test-Duel.ps1`; it uses UDP 17777 by default and launches two hidden players. Manual LAN/internet steps, scoped Windows Firewall examples and router forwarding guidance are in `HOSTING.md`. Actual remote-network verification remains unperformed.
